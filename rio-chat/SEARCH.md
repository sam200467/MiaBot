# Kimi 搜索接入

聊天仍使用 DeepSeek；音击/舞萌/中二基础曲目查询仍优先使用本地曲库。攻略、手法、体感和近期信息可以调用 Kimi 搜索。

## 本机配置

两个控制台界面上都有「Kimi 搜索设置」按钮，点它就会弹出设置窗口，粘贴 Kimi 开放平台 API Key 后保存。窗口不进行网络请求。按钮旁的状态会显示当前是「已启用 / 未配置 / 已关闭 / 配置损坏」，保存后立刻刷新。

命令行等价写法：`powershell.exe -NoProfile -ExecutionPolicy Bypass -File rio-chat/search-key.ps1`（加 `-Status` 只查状态，加 `-Read` 只读 Key，两者都不会弹窗）。

Key 用 Windows DPAPI 当前用户加密保存到 `rio-chat/search.local.json`，已加入 Git 忽略和公开版发布排除清单；换 Windows 用户/机器后需要重新填写。

保存后重新启动 Bot —— Key 只在聊天启动时读取一次，所以填完必须重启才会生效，界面上会提示这一点。QQ EXE 旁使用现有的上一级 `rio-chat` 目录，里面必须保留 `search-key.ps1` 和配置文件。不要把私人配置复制进公开仓库。删除配置或把 enabled 改为 false 可关闭搜索，不影响查分和曲库功能。

## 行为

- 文字攻略：`POST https://api.moonshot.cn/v1/tools/search_pro`，取最多5条正文片段。
- 视频：`POST /v1/tools/search`，取真实标题、链接、简介；不下载/观看视频，不能生成未经证实的时间点和手法。
- 网页阅读：`POST /v1/tools/fetch`，仅允许本轮搜索结果或用户提供的公开网页URL；不访问本机地址、不转发登录状态。
- 每条回复最多 2 轮联网搜索（程序预检索、模型工具轮各算一轮）和 2 次曲库检索。**轮数与实际请求数是两个计数**：空结果后的自动重查不占轮数，但占实际请求数，整轮实际请求硬上限 4 次（2 轮 × 每轮最多 1 次重查），计费按实际请求算。单次联网24秒超时（其中 search_pro 服务端限 20 秒，官方标注 Pro 耗时较长），启用搜索后整条聊天最多110秒。失败不自动重复收费请求（接口报错不触发重查），也不假装查到了内容。
- **检索入口四条**（2026-09-17 第四组路由改版、2026-09-18 第十三组补第四条）：① 用户在话里明说要查（联网／上网／搜索／搜一下／查资料／查阅／核实／查证／帮我搜，或「找攻略/视频/手元」）；② 攻略档词表命中（吃分／上分／推分／冲分／升段／水谱／地雷／体感／手法／攻略／运指／手元／怎么打／怎么练／怎么过／教我玩／教我打／适合练／上w6 这类目标，以及「简单／好打／偏难 + 谱面或等级或游戏名或真曲名」的难度评价）与时效问句（版本／更新／新曲／活动／最新 + 真的在问，且不是工具指令、不是曲库答得了的数量与定数）；③ 模型自己承认拿不准或答应去查（说明见下一条）；④ **模型按意图请求联网**——它标 intent、把可验证的外部事实抽成 factQuery，程序按策略表授权（见第十三组）。**其余一律不联网**，也不做「这句话算不算事实问答」的推断。
- **原作剧情（canon）另走一层**（2026-09-18 第十四组）。问「你之前是不是和 akari 打过真人 cs」这类**可由原作验证的事实问题**时，程序先在本地剧情索引 `knowledge/ongeki-story.json` 里查（纯规则、不调模型、不联网）。命中确认条目就**直接按本地事实作答，不再联网**；本地没有、或只有弱命中／单源条目时才允许模型按 `canon` 意图走拆分通道，且只发抽出来的客观事实子问题（`canonQueryCheck` 比 `factQueryCheck` 严：明确拒绝第一/二人称）。为什么与 self/roleplay 分开：self 硬禁止联网是为了防角色扮演乱搜，而这类问题**表面是 self、实质是事实**，被同一道闸门连坐时本地又没有可查的剧情层，模型只能凭印象否认——线上就是这么答错的（原作里确实有，是 2020 年 10 月的活动 ONE BULLET LEFT）。程序侧的剧情分类只看**结构**（剧情／章节／做过什么），不认具体事件名：「真人CS」「サバゲー」这类关键词属于索引的 aliases／keywords 数据，不往正则里堆，否则词表永远加不完。回答里否认了本地已确认的剧情时由 `canon-guard.cjs` 纠一轮，它的**误判防护比命中更重要**——否定否认（「不是没发生过」）、反问、引用／传信、记忆性否认（「我才不记得」）一律不触发，因为把一句本来正确的回答改错比漏掉一次糟得多。
- 工具指令（查分、B50、分表、定数表、算 Rating、绑定）和曲库能直接答的查询（定数、等级、收录数量、曲名、纯条件筛选）排在检索之前否决：检索回合会把工具清单从提示词里拿掉，误判成检索会让那一次查分直接失效。问 bot 自己的事（头像、画师、生日、模型、性格）另走一条「人设自述」，答案在人格设定里，网上搜不到也不该搜，模型说「我也不知道」时也不会被兜底网反手送去搜。
- 兜底网：本轮没判定要检索时，提示词里把「自行联网」这条口子关掉（`webRule(search, false)`），模型只被要求直说「不确定／没听过／查不到」。它这么说了而程序还没查过网，就按用户原词补一次真实检索（`needsResearchRepair`，在工具循环每一轮开头判定，所以曲库查空之后又说查不到也能补上）。这一补是替模型做的，查回来没有资料时保留它自己那句诚实的「不确定」，不整条替换成「没有拿到资料」。日志里 `理由` 写明这一轮为什么查／为什么不查（`用户要求查证`／`攻略或进度目标需要外部依据`／`默认不联网`／`工具指令`／`人设自述`…），漏没漏回看即可。
- 中间步骤（曲库查询、联网、改写重搜、重试）**全部静默执行**，用户只收到最终答复，不再先发一条「我去翻一下资料」。归属问题由 QQ 侧**引用用户原消息**解决：收到消息时就固定 `message_id`，无论中间经过几轮工具调用、群里又刷过去多少条，最终答复（含错误和超时兜底）都回复那一条（`qq-entry.cjs` 的 `__replyTo`）。引用不额外占发送配额，所以检索轮从「2 条」降到「1 条」，`perGroupPerHour` 的消耗减半。宿主若另外接了 `slowNotice` + `slowNoticeAfterMs`，整条回复超过该时长才会补一条状态提示，整条最多一条；默认不接、阈值 0 即关闭。注意程序预检索发生在任何模型调用之前，elapsed≈0，慢提示只可能出现在后续那几次联网前。
- 模型调用遇到传输层故障会自动重发同一条请求一次：网关用 200 返回非 JSON 或缺少 `choices`、body 读取中途断开、HTTP 429/5xx。超时或取消（预算已用完）、连不上代理、HTTP 4xx（鉴权、余额）不重试。日志用「空白回复后重画成功」和「网关故障后重试成功」区分模型侧和代理侧的问题，失败日志带截断后的响应片段。
- 成功结果在内存缓存，最多100项，重启后清空。缓存时长按资料变化速度分级：攻略/手法/運指类 24 小时，视频 12 小时，抓取的具体页面 6 小时，含版本/更新/活动等时效性关键词的查询只缓存 1 小时 —— 避免拿旧快照当现状回答。来源附检索时间，不能把快照当实时事实。
- **来源默认不显示**（2026-09-18 第十六组改，见下）：只有用户明确要出处、或模型确实引用了某条网页（给出 `sourceIds`）时，程序才把标题和链接追加进回复。模型只能选择本轮真实来源ID，编不出链接；正文仅作资料，不能覆盖系统指令。
- 搜索和模型均由平台按实际调用计费。群聊不会输出 Key；只有抽取的公开检索关键词发给 Kimi，不直接发送完整对话。
- 个人成绩推荐仍需要账号/权限和真实成绩筛选；网页搜索不能绕过这一限制。

## 验证

2026-09-17：增加程序预检索路由。攻略/冲分/手法/体感/时效事实和常见事实问答先搜索再生成；不依赖模型自评“会不会”。模型在其他问题上表示不确定时，也会先按用户原词查证。普通寒暄、曲库基础筛选、查分操作维持原流程；个人成绩保护优先于任何搜索。明确要求不联网时不预检索。

资料回答使用 DeepSeek 思考模式，减少角色示例干扰，并允许更完整的解释；普通闲聊仍走快速模式。陌生英文曲名按原词匹配来源，搜索聚合页过滤，B站专栏/动态保留正文，视频不冒充已观看。日服攻略只作为对应版本的玩家参考，不能当作国服实时收录/定数。

舞萌 Rating 目标另外使用已核对的 SSS+ 上限公式进行程序计算，帮助区别过渡练习与目标主力谱。规则来源：https://gamerch.com/maimai/533647 （2026-09-17核对，地区版本仍需确认）。不由公式推断曲目手感。

2026-09-17（第二组修正）：

- Rating 目标解析：`w6`／`万六`／`萬6`／`W5` 这类圈内写法先展开成 5 位数再匹配目标（原先只认 `\bw6\b`），否则目标解不出来，后面两项都无从谈起。B50 算式只在最近三轮出现舞萌时注入，避免把舞萌公式套到中二／音击的 Rating 目标上。
- 推荐下限：核算里新增程序算出的 `minConstant`——单张谱 SSS+ 上限刚好够到「目标÷50」的定数（16000→320→14.3，17000→15.2，15000→13.4）。要求主力推荐逐首写出定数并确认不低于它；低于下限的谱最多列 1～2 首且必须标成过渡或练习。来源里其他玩家的曲单反映的是他们各自的水平阶段，必须逐首按定数过一遍。
- 难度评价问法：口语评价词（简单／容易／好打／很难／偏难／适合新手…）与谱面或等级或游戏词同时出现时判定需要检索，例如「舞萌有没有一些比较简单一点的13+」。这类问题问的是玩家体感，只按定数从低到高挑歌正是曲库 caveat 禁止的做法。只有「简单」而无谱面/等级/游戏词（「简单介绍一下你自己」这类）不受影响。检索词按「游戏名+等级+简单 好打 谱面 推荐」重建，不再把「有没有一些…」的口语原句发给搜索引擎。
- 检索回答改用人设口吻（仍不注入示例对话，避免把答题带成寒暄），并在真正联网前发「找资料」提示；传输层故障重试一次。

2026-09-17（第三组：路由重做）：关键词表是开集，实测 25 句真实问法里 18 句触发不了检索，而且漏的正是需要外部依据的那些。改成按证据来源判定，`research-policy.cjs` 里是六级瀑布：

1. 用户明确要求不联网 / 寒暄 / 明确说「搜索」——不变。
2. 规则明确命中（攻略、冲分、难度评价、时效事实、事实问答）——不变，直通检索，不进分诊。
3. 工具指令（查成绩、B50、分表、定数表、算 Rating、`id数字`、绑定）——不检索。必须排在分诊之前：检索回合会把工具清单从提示词里拿掉，误判成检索会让那一次查分直接失效。
4. 曲库能直接答（定数、等级、收录数量、曲名），以及「只按条件挑几首」（推荐／挑几首／随便选 + 游戏或等级，且不含质量评价词）——不检索。
5. 域内 → 灰区，交分诊器。域信号：游戏名、难度档、**本地曲库里的真实曲名**（`knowledge.cjs` 的曲名索引，规范化后短于 3 字符的丢弃——「+♂」规范化后是空串，会匹配一切），以及评价或选曲类说法。话题（游戏、曲名、等级）可继承最近四轮，问法只认当前这句。
6. 其余 → 不检索，零额外调用。

曲名索引在 `loadKnowledge` 时建一次（三个游戏共 2845 个唯一曲名，单次匹配约 0.03 毫秒）；测试夹具或公开版缺 `rio-chat/knowledge/` 时安全退化成纯关键词行为。

修复从 PowerShell 7 启动 Node 时 Windows PowerShell 模块路径继承导致 Key 读取失败的问题；启动日志明确显示搜索启用/可用，回复完成日志记录联网次数和资料数量，不包含 Key 或检索正文。

2026-09-17（第四组：入口改由用户发起）：上线实测两类误判，方向和第三组的假设正好相反：

- 误检索：「宝宝你知道吗，你的头像是谁画的」命中了事实问答规则里的「是谁」，整句口语原样发给搜索引擎，搜回两条淘宝／简书软文，`attachSources` 在没有有效来源时把它们当「搜索结果（供核对）」贴了出来。同类还有「你是谁画的」——同一句话换个词，判据就反了。
- 漏检索：「你会不会打 inorganyx prayer?」四类域信号一个都不沾（本地曲库没有这首 Lanota 曲），直接落到「域外 → 零调用」，连分诊器都够不着；而它恰恰是本地答不了、最该外部检索的那一类。紧接着模型答了句「我可得先查清楚是哪里的谱面」，破承诺网又因为正则里只收「需要查／查阅／先确认」而没接住——用户看到的是「我这就去，别急」然后什么都没发生。

结论是判据本身不该承担「这句话算不算事实问答」这个开集问题，于是改成入口由用户发起 + 攻略档 + 兜底网（三条见上方「行为」）。删掉的东西：事实问答／时效性两条规则、整条灰区分诊链路（`classifyResearch`、`classifierPrompt`、`classifierInput`、`classifierReply` 的解析与 `plan.gray`）——闲聊不再产生任何额外模型调用，一次回复的模型调用次数回到「一问一答 + 检索后复述」。保留的自动档只有收口的两张词表（攻略、难度评价），因为它们都是「本地曲库答不了、模型只能凭印象编」的问法。

配套改动：`webRule(search, mayQuery)` 在本轮没判定检索时明确禁止模型自行联网，只要求它直说拿不准；`needsResearchRepair` 收敛到「模型说了却没查」，加收「先查／查清楚／我去翻／没听过／查不到」这类话术并豁免「人设自述」轮次，同时从 `chat.cjs` 的一次性前置检查挪进工具循环每一轮的开头——原先曲库查空之后模型再说「查不到」，程序已经没有第二次机会替它联网了。检索词里用户请求话术（「帮我联网搜索一下」）由 `requestWords` 剥掉，不再跟着发给搜索引擎。`#帮助` 两份文案各加一行说明怎么发起检索。

已知取舍：难度评价只认「简单／好打／偏难 + 谱面或等级或游戏名或真曲名」，以及攻略档词表里的说法；「推荐几个能稳定出分的」「这个谱面有什么坑」这类没命中的体感问法不再自动检索，改由兜底网在模型表示拿不准时补——要把它们也算进攻略档，在 `research-policy.cjs` 的 `strategy` 里加词即可（代价是「我今天出分了」这类自夸也会触发检索）。

离线：`node --test rio-chat/search.test.cjs rio-chat/knowledge.test.cjs rio-chat/chat.test.cjs`。

2026-09-17（第五组：中间步骤静默 + 引用回复）：检索轮原先要发两条消息——先是「我去翻一下资料」，再是正式答复。两条都占 QQ 侧每群每小时的发送配额（`perGroupPerHour` 默认 20），一次检索问答就等于花掉 10 次配额里的一次；而这句提示解决的问题（群里刷过去几十条之后，用户不确定这条在答谁）其实有个更省的办法：**引用原消息**。

改动：删掉 `researchNotices` 与 `webSearchNotice`，检索、曲库、改写重搜全部静默；QQ 侧收到消息时就把 `message_id` 存进 `__replyTo`，最终答复、错误提示、超时兜底一律带上 reply 段引用那一条。reply 段必须排在段列表最前，和原有的 @ 并存——@ 负责提醒，引用负责归属。引用不额外占配额，所以检索轮的开销是「1 条」，配额消耗减半。

两个附带修正：① 引用的消息可能已被撤回或超出可引用范围，QQ 会拒收**整条**消息（连答案一起丢），所以引用失败就摘掉引用重发一次，正文才保得住；② 为此必须把「相同内容抑制」的**登记**从发送前挪到发送成功后（`qq-onebot.cjs` 的 `noteSend`）——登记留在发送前的话，那次失败会在 60 秒冷却窗口里把它自己的降级重发挡掉，回复彻底发不出去。判定仍在发送前，防刷屏的语义不变。

慢提示没有消失，只是从「每次检索都发」变成「整条回复超过阈值才发」：宿主给 `adapter.slowNotice` + `slowNoticeAfterMs` 才启用，默认关闭。实测性质：程序预检索发生在任何模型调用之前（elapsed≈0），够不到阈值，所以这条只可能在后续那几次联网前触发。
顺带修掉 `qq-onebot.cjs` 里一个**裸 NUL 字节**（去重键的分隔符被写成了真的 `\u0000`，不是转义）：`grep` 一直把这个文件当二进制跳过、`file` 报 data、编辑器和 diff 都可能把它吃掉。已改成转义写法，运行时行为不变。

2026-09-17（第六组：定数裁决层）：结构化事实（曲名、难度、当前定数）以本地曲库为准，Web 只负责玩家评价、攻略和历史资料。这条是本项目最典型的错答来源：模型从社区老帖里抄来的定数是几个版本前的值（截图那条把 Dengeki Tube 写成 14.9，本地快照是 15.2），而且 spike 实测它**会在标注了「这是老帖的说法」之后照样把数字当事实报出去**——提示词禁不掉，只能由程序核对。

新增 `constant-guard.cjs`：回答发出前（`chat.cjs`）把模型自己那段话逐首过一遍，找到「曲名 + 定数形状数字」的搭配，按曲库当前值改掉，改动记进日志（`定数校正N处（曲名 旧→新）`）与 `result.research.constantFixes`。

两条闸门都是为了「宁可漏改，不可改错」：① **时效词**——数字所在那一句里出现「旧／老帖／以前／过时」就整句跳过，因为模型常写「老帖把它写成 14.9，那是旧数据」，改了这句就成了胡话；② **就近取难度 + 邻域限制**——数字离曲库值超过 1.0 就当它不是定数（BPM、年份、分数、物量都这样被滤掉），小于 0.05 视为本来就对。替换固定补一位小数：曲库里 15.0 存的是 15，直接替进去会得到「Angel dust 15」，而「15」在音游语境里读起来是等级。

**多游戏消歧**（这一版实测抓到的 bug）：`Love & Justice` 在音击是 MAS 14.7、在中二是 MAS 15.2，而老帖写的 14.9 离音击那张更近——纯按「数值最近」跨游戏挑，会把中二的旧值改到音击的定数上，比不改更糟。现在按 `knowledge.cjs` 新增的 `gameInText`（只从最近三轮用户消息里取唯一提到的游戏）消歧：点名的游戏优先；取不到线索而两款候选一样近时**放弃修改**。

配套的提示词口径（`research-policy.cjs` 的 `researchRule`）：三个游戏各自的档位切法（中二 14＝14.0~14.4／14+＝14.5~14.9、舞萌 14+＝14.6~14.9、音击 14+＝14.7~14.9，这三行是从本地曲库的 level/constant 分布量出来的），要求写定数前必须先用 `knowledgeQuery` 查过那一首，资料里的定数只能当体感参考、提旧值必须写明是旧数据。实测有效：模型开始自己写「老帖里说的 Love & Justice 14.9 已经过时了，我刚核对过，它现在是 15 级、定数 15.2」，并对没查过的曲子明说「那几首我这次没法核实现在的定数，只能当体感参考」。

2026-09-17（第七组：别名两级结构 + 昵称恢复）：曲名解析改成三级——**正式 alias 快速解析 → 本地曲库 → Agent 昵称恢复**。前两级都是确定性的，只有前两级都查不到才动模型。

**别名映射到正式曲名，不绑 songId。** 同一首歌可能同时收录在舞萌、音击、中二，各游戏的 songId、定数、收录版本完全独立；把别名钉在某个 songId 上就等于让它只对那一份数据成立，换款游戏就变成错答案。条目形状：`{alias, title, game}`——game 非空是那款游戏专属，game 空是跨游戏通用。解析时优先用当前对话的游戏作用域；**没给作用域又撞上歧义（同一叫法指向不同曲名）就是 null，绝不任选一个**。同名不同游戏（同一首歌两边收录）不算歧义：曲名一致，游戏数据的区分交给下游各自的曲库。旧文件（version 1，按 songId 存）照读：`configureAliases` 传 `resolveSong` 回调把 songId 换回曲名与游戏，写回时统一成 version 2；认不出的 songId 宁可报错也不静默丢数据。

第一级在宿主侧：`takase-core.cjs` 的 `resolveAliasTitle(word, game)`。解析规则**全部留在 `SongAliasStore`**（同一套 normalize、同一套 entries），聊天侧不实现第二套——它只拿到一个名字，从 `adapter.alias.resolve` 取。宿主曲库只有音击，所以 `#是什么歌`、`searchSongs` 这些命令路径固定传作用域 `"ongeki"`，别的游戏专属别名不会在那条路上命中。

第三级是昵称恢复（`rio-chat/alias-recovery.cjs` + `chat.cjs` 的工具循环）。曲库查空后给模型三级提示（换游戏 → 联网查或直接给正式曲名 `aliasGuess` → 说不确定）。但**主力不是模型自觉**：spike 实测模型能把「电管」认成 Dengeki Tube，却不会想起来回曲库核一遍，结果手上只有老帖的旧值、只能诚实拒答。所以程序侧加了**自动核对**——模型检索词里一旦出现曲库真曲名，立刻回本地库查一遍并进**同一条** evidence，零额外模型轮次；模型认出正式曲名的那一刻就被接住了。

自动核对只认**检索词**、不认资料来源正文：正文里顺带提到一堆曲名，全去核一遍等于把额度随机花掉——实测「电管」那条被核成了正文里先出现的 Love & Justice，模型拿到一条不相干的数据，真正要问的那首反而没核到。

**作用域以对话里点名的游戏为准**，模型自己在 `knowledgeQuery` 里填的 `game` 只是它的猜测，只在对话没提游戏时才拿来兜底。返回结构刻意分成 `facts` 与 `hints` 两个数组，结构上就不可能把提示当事实用：`facts` 是该作用域内查到的当前数据；`hints` 只出现在「用户点名了游戏、而这款里没有这首」的时候，内容是「这首歌在别款游戏有收录，可能不是同一首歌」，**不带任何定数**，也不进 `rechecked`。用户明确指定游戏时，**任何情况下都不拿另一款游戏的同名曲数据当当前事实**——Love & Justice 在音击是 MAS 14.7、在中二是 MAS 15.2，混起来就是错答案。只有用户压根没提游戏时，曲名索引记的那款才可以直接当恢复线索。`aliasGuess` 那条路同理：模型报的名字在本游戏查空时，只回一句「它在别款游戏有收录」的消歧提示，并明确要求不要假装它在本游戏里。

候选别名（`SongAliasCandidateStore`，与正式库同目录 `song-alias-candidates-qq.json`）：恢复成功后**只记不生效**，三条门槛全过才落盘——正式曲名已被识别、本地曲库**唯一命中**（一首歌几个难度算一首）、游戏上下文不冲突（对话说音击、命中的是中二就不记）。`#别名候选` 只读列出待确认项，`#驳回别名候选 <序号或别名>` 丢弃（沿用 `aliasDeleteQqs` 白名单，与删除别名一致）；确认仍走现有的 `#添加别名`，**不自动提升**——候选不进解析链，测试里专门盯着这条。候选上限 200 条，别名校验与正式库共用同一个模块级函数。

中文简称口径：Dengeki Tube 写作「电管」，「电击管」最多算兼容叫法。恢复提示里写死了这条，免得模型自创简称。

2026-09-17（第八组：承诺了却没查 · 线上实测）：现象是「用户说『好的帮我查一下吧』→ 模型回『那我帮你翻翻看』→ 什么都没查」，引用机器人上一句再问一次才对。三个缺口叠在一起，都不是消息串线：

① **兜底网只收「我去…」，漏了「我帮你…」**。`uncertainty` 里是「我去查／我去翻／我去找／让我查／查清楚／先查」，而模型实际说的是「那我帮你翻翻看」——同一个承诺的另一种说法，不在表里，于是最后一道网也兜不住。已补「帮你翻／帮你查／帮你搜／翻翻看／查查看／查一查／去翻／去查／去搜」。

③ 「未知指令」原先走 `sayPrivateOrGroup`，于是**在群里打了个 `#` 词的人会收到一条莫名其妙的私信**。这句话是对一条公开说出的话的直接回应，不是「未绑定／冷却」那类私人提醒，已改回 `sayOrigin`——回在原地。私聊场景不走 `sayOrigin` 的另一分支，行为不变。

**为什么没把「帮我查一下」加进 `explicit`**：想过，不能加。「帮我查一下我的成绩」「帮我查一下 id870」和检索是两回事，而检索回合会把工具清单从提示词里拿掉——一旦误判，那一次查分直接失效（见上面「工具指令必须挡在检索之前」）。所以请求词留在兜底网上，只在模型**答应了却没动**时才由程序补一次。

**为什么是「删」而不是「末尾纠错」**（用户 2026-09-18 追加）：留着一条不合格推荐、只在末尾补一句「它其实不在这一档」，读者第一眼看到的仍然是那个推荐，得读到脚注才知道不算数。删除规则刻意保守——`dropRecommendations` 只删「能被标点切成完整一小块」的范围（列表项整行，或包住它的那一小段），块里**不能还有别的曲名**（逐字抠名字会留下「Titania 和 都能上分」这种断句，比不删更糟），删完剩下不到十个字的也不删（整条回复就是那条推荐时，删了就没内容可发了）。拿掉之后接缝上多余的标点一起吃掉，免得留下「，另外…」或孤零零的「。」。删掉与保留分别记 `result.levelDropped` 与日志里的「程序删除推荐：曲名」。

**版本/地区口径**：本地曲库是**快照**，三份快照的 `scope` 自己就写着「不保证所有地区版本一致」「不能当作日服/国际服实时收录证明」。程序替模型说的话（重写指令、末尾说明）统一走 `scopeNote` + `snapshotCaveat`，说成「程序用本地曲库快照（2026-09-16）核对的结果；该快照不代表国服/日服实时收录」——「快照里是这样」不能讲成「国服现在就是这样」，地区版本差异要留给读者判断。重写指令里也把这条写死了：档位以快照为准，但不要宣称国服/日服实时。

2026-09-18（第十二组：结果为空后重建检索词 · 队列里最后一项）：第一次搜索什么都没拿回来时，程序**重写检索词再查一次**，整轮只给一次。

触发面刻意收窄——只认「搜了，但没拿到可用资料」：`sources` 为空，或者回来的每一条正文和摘要都是空的。**调用本身失败（超时、HTTP 错误、Key 失效）不重查**：那是链路问题，换词也白搭，重试只会多花一次调用。另外把「结果一条都没匹配上要问的那首曲子」也算进来——`addSources` 按 entity 过滤之后为空，程序给模型的 note 本来就写着「应使用原名换一个查询」，那正是该换个写法再搜的场合。

重写不是换同义词：`research-policy.cjs` 的 `rewriteQuery` 用**已经认出来的东西**重建一句——游戏名（优先日文原名，日文社区的同人攻略最多；对话没点名时，这首曲子在曲库里只收录一款就用那款）、正式曲名（曲名索引认出来的；别名解析过的写法走到这里已经是正式曲名）、问题类型（攻略／定数／评价／冲分各配一个日文词，例如攻略→`攻略 譜面 手元`）、等级或 Rating 目标（已经解析出来的数字比任何同义词都硬）。曲库外的新曲只能用 `plan.entity` 当锚点。**重建不出和原句明显不同的一句就返回 null**，直接不重查——同一句话再搜一次纯属浪费额度。视频检索词换成文章检索：要看的是正文，不是标题列表。

**两个计数分开**（收尾时补，见下）：`webCalls` 是**逻辑搜索轮数**（工具预算、是否已检索过、回复长度放宽都看它），新增的 `webRequests` 是**实际发出去的网络请求数**——计费按它算，所以它有一道整轮的硬上限 `MAX_WEB_REQUESTS=4`，卡在所有请求的唯一出口上，任何路径都绕不过去。原来只有一个 `webCalls`，重查不占它等于绕过了唯一的预算；拆开之后重查**不占轮数、但必须占请求数**。日志记「联网N轮／实际请求M次」，两个数一眼能对上账。

边界：重查属于**同一次搜索过程**——`webCalls` 不加（不占那两次联网配额）、不给 QQ 发状态消息（`web()` 里的慢提示整轮最多一条，重查顶多触发那一条，不会再补）；重查时**放开站点限制**（原来那份 `sites` 是配第一句的，换了语言还锁在同一批站点上多半还是空）；两次都空就停下不再循环，由程序在返回给模型的数据里写明「换了检索词（…）再查一次仍然没有可用资料；这一项要说清楚资料不足，不要凭印象补」，非 soft 轮次照旧整条替换成「这次没有拿到可核实的网页资料」。日志记「结果为空后重建检索词（…）」。

2026-09-18（第十三组：意图—授权 + factQuery 接进主链路）：先跑专项 spike（`router-spike.cjs`，33 条用例、真实模型 + 桩网页）——现实/时效 5 条全部自动联网、模糊 3 条全部不搜、玩梗/创作/假设 3 条全部不搜，闲聊误联网 0、该查没查 0、被否后谎称网络故障 0。数字干净，于是接进生产。

**结构**：理解语言交给模型（它标 `intent`、把可验证的外部事实抽成 `factQuery`），管权限留在程序（只对枚举值做映射，**永远不匹配用户原句**）。授权三条来源，优先级从高到低：① 入戏/人设只能走**拆分通道**——只执行通过三项形式检查的 `factQuery`（不是原句、不带假设语气、不指向 bot 自身），纯人设互动直接拒绝；② 程序自己判定的检索（攻略/体感词表、时效规则、兜底网）照旧放行；③ 模型请求，`intent` 含 `research`／`explicit` 才开通，**未知取值与缺失一律拒绝**。被拒时模型会收到一条纠正（「程序未授权联网…」），要求它把事实抽成 factQuery 或直接回答——不把未授权说成网络故障，也不许写「我这就去翻」。

**生产实测**（`rio-chat/intent-smoke.cjs`：走真 `requestReply`、真模型、桩网页）跑出三个 spike 没暴露的坑：

**查到的追加链路**（按用户要求先定位再改，不在文本上删字）：`chat.cjs` 的 `web()` 把每次联网里**通过实体过滤**的结果都塞进 `sources` 数组（`sourceStats.relevant`），这数组**从此不清**；然后只要 `webCalls` 为真就无条件调用 `search.cjs` 的 `attachSources`，而它**在模型没给 `sourceIds` 时会退化成「把前两条原始结果当『搜索结果（供核对）』贴出来」**。于是：这轮只要发生过任何一次检索（预检索、兜底网、模型请求），哪怕答案完全由本地资料完成，那两条无关结果也会被贴上去。`localAnswered` 成立时既不清理也不隐藏。

**改法**：把来源拆成四个状态——`retrieved`（搜回来的）→ `relevant`（通过实体过滤的）→ `cited`（模型点名引用了的，即 `sourceIds`）→ `displayed`（真正展示的），**只有 cited 才可能展示**：

- 默认一条都不显示。**「这一轮搜到过某网页」不等于「它是回答依据」**；
- 用户明确要出处（来源／出处／链接／查证）时才给：**本地条目自带的 source 优先**（术语条目、剧情条目、角色档案、曲库快照的 `source`/`scope`），其次才是本轮引用到的网页——**不为凑链接再联一次网**；两者都没有就直说没有，不编；
- 模型的 `sourceIds` 指向哪条就只展示哪条（`attachSources` 新增 `citedOnly` 选项：默认按引用过滤，用户要出处时传 `false`，由调用方把「本地 source + 已引用网页」挑好）；回退到「贴原始结果供核对」的那条老路只留给 spike，生产侧走不到。

来源明细仍进日志：「来源 搜到N/相关M/引用K/展示J」+ 引用到的标题，调试不受影响。测试覆盖：搜到过网页但没引用→不挂链接（线上那两条实录）、引用了才展示且只展示引用那条、用户要出处时给本地 source 且零联网。

（同日补，冒烟改出来的一条）reset 那条一开始**还是不对**：用户只说「早上好」，梨绪主动接了一句「刚才群里的事我早翻篇了」——语气是软了，但**把那段端出来了**，等于替对方转述冲突。两处提示词补了明文禁令（群上下文那段的**末尾** + persona 的回落段），并写进具体例子：「用户只说一句早上好，就只回问候，**连「我已经翻篇了」都不用说**（说了等于把它端出来）」。实测四次里仍犯两次（模型很想证明自己没被影响），于是按项目老规矩加**程序兜底**：当前句没有指代群里的信号（群里/他们/刚才/那个人…）、而回答里出现「群里／那两位／刚才那事／翻篇／不迁怒」这类表态时，给一次重写（话术：「删掉那部分，只按用户这句话回答；不要解释自己的情绪状态」），改不掉就记 `语气泄漏未纠正` 日志、不再纠缠。改完连跑四次全部干净。冒烟脚本也加了对应断言（`quietAbout`），免得以后靠肉眼。
